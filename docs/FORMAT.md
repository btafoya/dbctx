# FORMAT.md

# dbctx Output Format Specification

**Format Version:** 1.0

## Purpose

This document specifies the canonical output formats generated by dbctx.

The document format version is independent of the application version.

------------------------------------------------------------------------

# Design Goals

-   Stable
-   Deterministic
-   Human-readable
-   Machine-readable
-   Backward compatible
-   Vendor neutral

------------------------------------------------------------------------

# Output Directory

``` text
.ai/dbctx/
├── schema.json
├── schema.md
├── metadata.json
├── relationships.json
├── graph.mmd
└── tables/
```

------------------------------------------------------------------------

# Common Metadata

Every JSON document begins with:

``` json
{
  "format": "dbctx.<type>",
  "format_version": "1.0",
  "generator": {
    "name": "dbctx",
    "version": "0.1.0"
  },
  "generated_at": "2026-01-01T00:00:00Z"
}
```

Required fields:

-   format
-   format_version
-   generator.name
-   generator.version
-   generated_at

------------------------------------------------------------------------

# schema.json

The canonical representation of the database.

## Root Object

``` text
schema
├── metadata
├── tables[]
├── views[]
└── relationships[]
```

## Database Metadata

Fields:

-   database
-   engine
-   engine_version
-   default_charset
-   default_collation

Optional:

-   attributes

`engine` is one of `mysql`, `mariadb`, `sqlserver`, `postgres`, `sqlite`.

`default_charset` and `default_collation` are null on SQL Server and
SQLite, which have no database-level charset.

`attributes` is a map of engine-specific facts; see [Attributes](#attributes).

## Table

Required:

-   schema
-   name
-   engine
-   charset
-   collation
-   comment
-   columns
-   indexes
-   foreign_keys

`schema` is the object namespace: the database name on MySQL and MariaDB,
the SQL Server schema (for example `dbo`) on SQL Server, the PostgreSQL
schema (for example `public`) on PostgreSQL, and the SQLite database name
(`main`, `attach1`, ...) on SQLite.

`engine`, `charset` and `collation` are null on SQL Server, PostgreSQL and
SQLite, none of which have a per-table storage engine or MySQL-style
charset. Null fields are still emitted.

Optional:

-   analysis
-   ai
-   attributes

`attributes` is a map of engine-specific facts; see [Attributes](#attributes).

## Column

Required:

-   name
-   ordinal_position
-   data_type
-   full_type
-   nullable
-   default
-   auto_increment
-   primary_key
-   unique
-   comment

Optional:

-   generated
-   expression
-   attributes

`attributes` is a map of engine-specific facts; see [Attributes](#attributes).

## Index

Fields:

-   name
-   unique
-   columns\[\]
-   index_type

Optional:

-   attributes

`index_type` is the value reported by the engine (`BTREE` or `HASH` on
MySQL and MariaDB, `CLUSTERED` or `NONCLUSTERED` on SQL Server, always
`BTREE` on SQLite, which has only one physical index structure, or the
PostgreSQL access method name such as `btree` or `gin`). It is never
normalized across engines.

## Foreign Key

Fields:

-   name
-   columns\[\]
-   referenced_schema
-   referenced_table
-   referenced_columns\[\]
-   on_update
-   on_delete

Optional:

-   attributes

`referenced_schema` follows the same rule as `Table.schema` and is always
populated, so a reference is unambiguous on engines where table names
repeat across schemas.

SQLite never reports a foreign key's declared constraint name, even when
the DDL gave one; `name` is synthesized as `<referenced_table>_fk<n>`.

## Attributes

`attributes` is a `BTreeMap<String, JSON value>` of engine-specific facts
that do not fit the fields above, present on `DatabaseMetadata`, `Table`,
`Column`, `Index`, `ForeignKey` and `View`. It is empty and omitted from
the document for MySQL, MariaDB and SQL Server, so their output is
unchanged. A reader must default it to empty when absent, per the format's
readers-ignore-unknown-fields rule; format_version stays `1.0`.

PostgreSQL:

-   Table: `access_method`, `tablespace` (when not the database default),
    `row_security` (always, boolean)
-   Column: `identity_generation` (`ALWAYS` or `BY DEFAULT`, when the
    column is an identity column), `collation` (when not the column's
    default collation)

SQLite:

-   Table: `without_rowid`, `strict` (present and `true` when the table
    was declared that way; absent otherwise)
-   Column: `hidden` (the raw `PRAGMA table_xinfo` code: `1` hidden, `2`
    virtual generated, `3` stored generated; absent for an ordinary
    column)
-   Index: `origin` (the raw `PRAGMA index_list` code: `c` created by
    `CREATE INDEX`, `u` a `UNIQUE` constraint, `pk` the primary key)

Example, a PostgreSQL table using `GENERATED ALWAYS AS IDENTITY`:

``` json
{
  "name": "id",
  "data_type": "integer",
  ...
  "attributes": {
    "identity_generation": "ALWAYS"
  }
}
```

# relationships.json

Contains only relationship information.

``` text
relationships[]
    from_schema
    from_table
    from_columns[]
    to_schema
    to_table
    to_columns[]
    constraint
```

Tables are sorted alphabetically.

Relationships are sorted by:

1.  from_schema
2.  from_table
3.  to_schema
4.  to_table
5.  constraint

------------------------------------------------------------------------

# metadata.json

Contains project-level information.

Example fields:

-   database
-   engine
-   engine_version
-   table_count
-   view_count
-   foreign_key_count
-   generated_at

Goals:

-   Readable
-   Token efficient

``` text
Columns

Indexes

```

# graph.mmd

Mermaid ER diagram.

-   Valid Mermaid syntax

------------------------------------------------------------------------

# tables/

Each table is exported separately.

Example:

``` text
tables/
    customers.json
    orders.json
```

On SQL Server, PostgreSQL and SQLite the schema is part of the file name,
because more than one schema may hold tables of the same name:

``` text
tables/
    dbo.customers.json
    sales.customers.json
```

Each file contains:

-   metadata
-   one table definition

------------------------------------------------------------------------

# Ordering Rules

Deterministic ordering is REQUIRED.

Sort:

-   tables
-   columns
-   indexes
-   relationships
-   views

Alphabetically unless database ordinal position is semantically
meaningful.

Tables and views are sorted by schema, then by name.

------------------------------------------------------------------------

# Null Values

Use explicit JSON null.

Do not omit fields solely because values are null.

Optional sections may be omitted only when disabled.

------------------------------------------------------------------------

# Optional Sections

Enabled with flags.

## --analyze

Adds:

``` json
{
  "analysis": {
    "kind": "lookup_table",
    "confidence": 1.0,
    "evidence": [
      "deterministic_rule"
    ]
  }
}
```

Analysis must be deterministic.

------------------------------------------------------------------------

## --llm

Adds:

``` json
{
  "ai": {
    "generated": true,
    "confidence": 0.91,
    "summary": "...",
    "notes": []
  }
}
```

Requirements:

-   Clearly labeled
-   Never overwrite facts
-   Easily removable

------------------------------------------------------------------------

# Compatibility Rules

Readers MUST ignore unknown fields.

Writers MUST preserve format_version.

Breaking structural changes require a new major format version.

------------------------------------------------------------------------

# File Naming

Lowercase.

Stable.

No timestamps in filenames.

Schema-qualified on engines where table names may repeat across schemas.

------------------------------------------------------------------------

# Encoding

-   UTF-8
-   Unix line endings
-   Pretty-printed JSON (2 spaces)
-   Trailing newline

------------------------------------------------------------------------

# Checksums (Future)

Future versions may include SHA-256 manifests for generated artifacts.

------------------------------------------------------------------------

# Validation

Generated artifacts must validate against the published JSON Schema for
their format version.

------------------------------------------------------------------------

# Canonical Source

The canonical source for all output formats is the internal schema model
defined by the library.

Exporters must not query the database directly or derive facts outside
the canonical model.
